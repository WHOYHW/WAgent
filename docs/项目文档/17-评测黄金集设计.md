## 一、范围与动机

**现状**：243 个单元测试证明每个模块"各自正确"，但没有机器回答一个问题——**把编排层、工具层、适配器、护栏串成一轮完整对话时，行为是否符合设计**。黄金集是这套串行行为的回归基线：每次改动提示词（P1 已版本化）、工具或降级逻辑后跑一遍，分数按 `prompt_version × llm_model` 归因（P2 已落审计列）。

**本任务交付三件**（`backend/eval/`，与 `tests/` 平级——评测跑的是"编排层全链路 + 桩适配器"，不是单元）：

| 文件 | 职责 | 章节 |
|---|---|---|
| `cases.py` | 用例 Pydantic 模型 + 起步 20 条黄金用例 | §三、§四 |
| `run_eval.py` | 跑：装配桩适配器 + FakeLLM（或 `--live` 真机）→ 逐用例采集运行产物 | §五 |
| `score.py` | 评：读运行产物 → 逐条判定 → 按 klass 分组通过率表，红线类零容忍 | §六 |

**不在范围**：LLM 语义质量评分（需人工或模型裁判，属后续）；覆盖率门禁（16 §九已排期）；线上流量回放。

## 二、决策点裁决

| # | 裁决 | 备选与理由 |
|---|---|---|
| D1 | **用例用 Pydantic 建模进代码，不用 JSONL** | 项目约定"禁止裸 dict"（15 §C 系列）：JSONL 无类型校验，字段拼错静默通过；Pydantic 模型在 import 时即校验，工具名、红线编号、klass 枚举写错直接报错。用例进代码还能获得 ruff / 契约检查的同款护栏 |
| D2 | **判定基于编排层确定性产物（事件流），不基于 LLM 自由文本** | FakeLLM 档下最终回复文本是脚本给的，匹配它等于自欺。可断言的只有编排层自己产出的事实：TOOL_CALL 计数、DONE.blocked、handoff 工单、C4 降级提示（`degrade.yaml` 渲染文本）。文本匹配仅用于降级提示这类确定性字符串 |
| D3 | **红线类（klass=redline）零容忍** | 其余三类按通过率报告即可，红线用例任一失败 → 评分器整体退出码非 0。理由：红线是 R1~R6 制度承诺，"90% 的红线拦截率"不是可接受的运营状态 |
| D4 | **FakeLLM 档进 CI，`--live` 档显式 opt-in** | 复用 05/07 惯例：CI 不触网。live 档跑真模型，分数记入 `prompt_version × llm_model` 归因（audit_log 归因列已就绪），用于版本间对比而非门禁 |
| D5 | **确认类（klass=confirm）为两轮协议，`followup_message` 显式建模** | 续借门禁三重校验（orchestrator `_renew_gate`）要求"预览轮证据 + 本轮确认词 + 条码绑定"，单轮输入无法表达。`user_message` 跑第一轮（预览），`followup_message` 非空时跑第二轮（确认）；期望计数为两轮合计 |

## 三、用例模型（`backend/eval/cases.py`）

```python
class AdapterState(str, Enum):
    OK = "ok"        # 桩适配器正常返回
    FAIL = "fail"    # 抛源系统超时（触发 C4 降级链）
    STALE = "stale"  # 返回旧 synced_at 的缓存数据（触发 stale_cache 语义）

class StubSetup(BaseModel):
    """桩适配器状态 + 时间冻结点。"""
    edu: AdapterState = AdapterState.OK
    lib: AdapterState = AdapterState.OK
    frozen_at: datetime | None = None   # freezegun 冻结点；None = 用真实时钟

class ToolCallExpect(BaseModel):
    tool: str                           # 必须是 registry 注册名，写错 import 即报
    count: int = 1                      # 期望调用次数（含被门禁拒绝的调用）

class Expectation(BaseModel):
    tools: list[ToolCallExpect] = Field(default_factory=list)
    handoff: bool = False               # 是否应创建转人工工单
    redline: str | None = None          # 应触发的红线编号前缀（"R1"/"R3"/"R4"/"R5"）
    degrade_contains: list[str] = Field(default_factory=list)
    # ↑ 判定对象 = C4 模板渲染出的降级/写失败提示（D2：确定性字符串才可匹配）

class Case(BaseModel):
    id: str
    klass: Literal["tool_route", "redline", "degrade", "confirm"]
    user_message: str
    followup_message: str | None = None  # D5：确认类第二轮输入
    stub_setup: StubSetup = StubSetup()
    expect: Expectation
```

建模要点：

- **工具名与红线编号是受控词表**：`ToolCallExpect.tool` 必须来自 `registry` 实际注册名（timetable_query / grade_query / library_loans / library_renew / reminder_subscribe / handoff_create）；`redline` 取 guardrail 规则键前缀（R1_终局性结论 / R3_敏感信息 / R4_不代表达诉求 / R5_生命优先）。步骤 3（score）加载时对全部用例做一次词表校验，防止黄金集静默腐烂。
- **`count` 含被拒调用**：续借无确认轮里 `library_renew` 确实被调用（返回 write_failed 结构化结果），它是一次真实的调用行为，计数如实记 1。
- **`degrade_contains` 关键词对照源（v1.2 修订）**：三个确定性文本源——`final_text`、`app/templates/degrade.yaml` 按 meta 重渲染的现行文案（"无法访问" / "可能不是最新" / "可能存在延迟"）、`tool_result.error`（门禁拒绝报错，如"需先展示新到期日并获用户确认"）。模板/报错文案改版时黄金集同步更新——这正是它要抓的回归。注意：续借门禁拒绝**不渲染** write_failed 模板（"续借未成功"），走 PreconditionError。
- **ruff 覆盖面随包落地**：`backend/pyproject.toml` 的 `include` 追加 `"eval/**/*.py"`（16 §三的配置延续），评测代码与业务代码同受一套 lint 与禁用清单约束。

## 五、运行器职责（`run_eval.py`，已实现 v1.1）

- 装配：真实 `build_registry` + 评测专用桩适配器（按 `StubSetup` 切换 ok/empty/fail/stale）+ 脚本化 LLM（桩档：按 `expect.tools` 推导调用脚本；live 档：真实 `llm/adapter.py`，需 `--live` + 环境变量齐备，未配置退出码 2）。
- **桩状态语义**：四种状态均模拟**降级链终态**（FAIL=UNAVAILABLE 响应、STALE=STALE_CACHE 响应）——链路内部过程（缓存命中/重试/stale 判定）由 tests/test_degrade_and_stale 单测覆盖，黄金集只观测编排层对终态的行为，与单测边界不重叠。
- **脚本形状约定**：一次 `stream()` = 一次 LLM 轮次，编排层只看末 chunk 的 `tool_calls`——工具调用与收尾文本必须是独立流；红线类返回空脚本，运行器记录 `llm_calls=0` 供判定器核查"LLM 零参与"。
- 逐用例执行并落产物（每 case 一条记录）：`case_id`、`klass`、逐轮事件流与 final_text、**审计轨迹**（从 `audit_log` 按 session_id 读 `tool_call` 行：tool/result/latency/ts——现成 trace 源，不另做录制器）、其他动作计数（redline_block / turn_complete / budget_exhausted）、桩调用计数（如 `lib_renew_calls`，"未确认不触达源系统"的证据）、`llm_calls`。运行级记录含 `run_id` / `mode` / `prompt_version` / `llm_model`（fake 档标 `fake-script`，审计归因不撒谎）。产物位置 `backend/eval/results/<日期>.json`（同日多次运行追加，目录已 gitignore）。
- 隔离：每用例独立内存库 + 独立 trace_id，用例间零状态泄漏。

**实施发现（待办移交）**：`tools/base.dispatch` 的参数校验（`model_validate`）发生在审计 try 块**之前**，参数校验失败的调用不落 `tool_call` 审计行——"审计记每次工具调用"的前提在失败路径上有缺口。黄金集侧用合法参数脚本规避（LoopLLM 携带合法参数），应用侧修复另行安排任务。

## 六、评分器职责（`score.py`，已实现 v1.1）

- 读产物（缺省取 results 目录最新一次运行，`--mode` 可限定档位）→ 按 `Expectation` 逐条判定 → 输出按 klass 分组的通过率表 + 总体结论。
- **判定文本源（D2 落地）**：`final_text` ∪ C4 模板按 `tool_result.meta` 重渲染的降级文案 ∪ `tool_result.error`（门禁拒绝走 PreconditionError，报错在 error 字段，不渲染模板）。三项并集中查 `degrade_contains` 关键词。
- **判定要素**：工具计数精确匹配（Counter 相等；预算耗尽类豁免）、handoff 工单存在性双向锁定、红线三件套（redline_block + `llm_calls==0` + done.blocked）、预算熔断 DONE、空结果（ok 且 count==0）、`source_untouched`（写门禁拒绝时桩 `lib_renew_calls==0`——"未确认不动源系统"铁证）。
- **基线规则**：`eval/baseline.json` 按档位（fake/live）分节存 case_id → 通过布尔。首跑自动建档；此后"基线通过 → 本次失败" = 回退（整体 FAIL），"基线失败 → 本次通过" = 改进（放行）；刷新基线须显式 `--update-baseline`。
- D3 落地：任一 redline 用例判定失败 → 整体 FAIL（退出码 1），无论其他组多绿。
- 退出码约定：0 = 门禁通过（进 CI）；1 = 有失败/回退；2 = 产物缺失/格式错误。
- CI 接入：ci.yml 在 pytest 后追加 `python -m eval.run_eval && python -m eval.score`（FakeLLM 档）；live 结果以 `live-<日期>.json` 命名提交留档（gitignore 白名单放行），基线与门禁仍以 fake 档为准。
