# 提醒引擎 R4b — 四闸全序与下发闭环设计（gate.py + engine 接线）

> 上游：09 §2.4（门序表）/ §2.5（下发）/ D2（静默）/ D3（claim+CAS）/ 10 §7.4（P0 语义）/ 13（渲染）。
> 里程碑意义：本切片完成后，dev stub 日志第一次出现真实推送内容——M5 用户价值可见。

## 一、管线总览（scan_once 内新增的下半段）

```
求值器候选集
  │ 门1 静默（claim 前，跳过不占坑）
  │   非 P0 ∧ 校园本地时 ∈ [quiet_start, quiet_end) → INSERT skipped_quiet（dedup_key 追加 "|quiet"）→ 移出批次
  │   P0 直通
  │ 门2 claim（每候选一次，claim 粒度 = dedup 身份）
  │   INSERT status='claimed', claimed_at=now
  │   ├ IntegrityError → CAS 认领自愈：UPDATE ... WHERE status='claimed' AND claimed_at < 阈值
  │   │                  rowcount=1 → 获得续发权（孤儿行接管）；rowcount=0 → 让路跳过
  │ 门4 频控（claim 后计数，消 TOCTOU）
  │   SQL 拉学生当日 billable 行（JOIN subscription.priority）→ daily_dispatch_count 纯函数计数
  │   非 P0 超额（base + 已 claim 批内序次 > daily_cap）→ UPDATE status='skipped_quota'；P0 永不计数
  │ 门3 聚合（渲染分组，不改变 claim 粒度）
  │   按学生分组：单条 → 自身文案；多条非 P0 → "【提醒汇总】共 N 条"编号拼接；P0 永不聚合单发
  │ 下发
  │   _push_adapter.send(student_id, channel, content)（每消息一次）
  │ 终态
  └   单语句 UPDATE：status ← receipt.status，pushed_at ← now，is_degraded ← receipt.is_degraded
```

## 二、设计决策（定版）

### D1 门序微调：频控在聚合之前执行

09 §F3 门序文字为"静默 → claim → 聚合 → 频控"。实施定版为**静默 → claim → 频控 → 聚合**：频控的拒绝动作是行级 `UPDATE status='skipped_quota'`，与渲染无关；先筛掉超额候选再渲染，避免为注定不发的消息拼字符串。语义等价性：聚合只改变"几条候选拼一条消息"，不改变谁被拒；两序下同一候选集的最终状态集相同。生命周期图（09 §2.4）的 `claimed ──频控超额──▶ skipped_quota` 与本序一致。

### D2 claim 与 CAS：冲突即自愈检查

- INSERT 撞 `uq_dispatch_dedup` → **先别让路**：对已存在行尝试 CAS 续锚
  `UPDATE reminder_dispatch SET claimed_at=:now WHERE id=:id AND status='claimed' AND claimed_at <:now-阈值`
  （`rowcount==1` → 本实例接管孤儿行，当前候选**有权续发**；`rowcount==0` → 行已终态或锚新鲜，让路跳过）。这一步是 D3"claim 后崩溃不永久卡死"的闭环，且复用 `claimed_at`（迁移 0003 已落表）。
- 会话内用 `begin_nested()`（SAVEPOINT）包住每次 INSERT：IntegrityError 只回滚到占坑点，不污染主事务。
- 续发沿用原行 dedup 身份，发送成功后照常终态回写该行。

### D3 频控：纯函数接 SQL 查询侧

按 09 `daily_dispatch_count` docstring 的参考形态，SQL 做**粗剪枝**（学生 + `dedup_date >= day-1` + JOIN priority），精确归属（sent 按 pushed_at、claimed 按 dedup_date、P0 剔除）交给既有纯函数——**零第二份计数逻辑**。批内已 claim 的行由 SQL 自然计入（claim 后计数），TOCTOU 最坏偏差 = 并发窗口 1 条，09 D3 已接受。

### D4 静默门判定用校园本地时，跨午夜窗口

`_in_quiet(local_t)`：`start <= t or t < end`（start>end 时窗口跨午夜；start==end 视为全天静默）。时区用 `CAMPUS_TZ`（13 §D1 同源常量，替代 09 的"服务器本地时"——R3b 已定版单时区假设）。`skipped_quiet` 行的 `dedup_key` 追加 `|quiet` 后缀落独立命名空间（D2 裁决关键细节：不占坑，否则 07:05 重放被唯一约束顶掉 = 跳过变永久丢失）。

### D5 聚合消息格式（定版）

单候选：13 的模板原样。同学生同批多条非 P0：

```
【提醒汇总】共 2 条：
1. 【图书到期提醒】你有 1 本书3天后到期：…
2. 【上课提醒】14:00 《数据结构》在 敬贤楼201 上课，主讲 王老师。
```

P0 **永不聚合**，混批时 P0 单独一条、其余合一条。聚合消息发送后，**组内全部 claimed 行**共享同一回执终态（一次通道调用对应 N 行落同状态；claim 粒度不变，去重身份仍一一对应）。

### D6 引擎接线与 ScanStats 扩展

- `ReminderEngine.__init__` 增加 `push_adapter` 注入（main.py 传进程级单例；None 时引擎不发送，仅求值——保住"enabled=false/未配置通道也安全空转"的既有语义）；
- `scan_once` 收集候选列表 → 候选非空且有适配器 → `gate.dispatch(...)`（自开独立会话，异常并入既有 scan_errors 兜底，不杀心跳）；
- `ScanStats` 扩展计数：`sent / failed / degraded / skipped_quiet / skipped_quota / duplicates`（默认 0，向后兼容）；`to_dict()` 同步补列，AC-3b 的逐字段断言随行更新。

## 勘误（2026-10-27 实测复现后修复）

`_billable_rows` 原实现为双实体 `select(ReminderDispatch, priority)`，返回 Row 的属性键只有两个实体名；`daily_dispatch_count` 鸭子访问 `r.student_id / r.status / r.pushed_at` 直接抛 `AttributeError`。触发条件：同学生当日已有 ≥1 条 sent 行（第一次推送成功后的下一个 tick 必现）→ 整批候选丢失、scan_errors=1，M5 第二次扫描即进入"每次都炸"状态。

修复：查询改为平铺列 select（student_id / status / pushed_at / dedup_date / priority），Row 键即列名，纯函数零改动。回归测试 AC-5h 两例（cap=2 第二条照发 / cap=1 第二条 skipped_quota）在旧实现下必红、修后转绿。

原 27 项测试未抓到的原因：故障前置条件（有订阅 + 当日已发行）从未被同时构造——ac5b 二扫无订阅被 JOIN 滤空，ac5d 查询时库中尚无 sent 行。教训已记：**频控基数"跨批生效"语义必须有独立用例锁住**。
