## 1. 数据契约 ToolMeta —— 所有工具出参的「身份证」

**是什么**：每个工具的出参模型顶层都必须携带 `ToolMeta` 字段：

| 字段 | 含义 |
|---|---|
| `source` | 数据来源系统（edu_system / library_ils / cache / card_system / internal） |
| `synced_at` | 数据同步时间（ISO 8601 含时区） |
| `degrade_status` | 五级降级状态（见第 2 节） |
| `is_stale` | 是否为陈旧数据（见第 3 节） |
| `stale_reason` | 陈旧原因（可选，如 source_timeout） |

**为什么**：LLM 输出是概率性的，数据可信度必须由结构化字段承载而不是靠模型"自觉说明"。没有 meta，模型可以把 2 小时前的缓存课表描述成"你今天的课表"（风险 K3 幻觉）；有了 meta，前端拿到 `is_stale=true` 就强制渲染"非实时"角标——**可信度是数据的一部分，不是话术的一部分**。

**设计要点：单一事实来源（SSOT）**

- `ToolMeta` 是 Pydantic 模型（[schemas/meta.py](file:///e:/Agent/backend/app/schemas/meta.py)），JSON Schema 由 `model_json_schema()` 自动派生，禁止手写——改模型，Schema 自动变，永远不会出现"文档和代码不一致"。
- `degrade_status` 与 `is_stale` 的计算收敛在 `build_tool_meta()` / `compute_is_stale()`（[degrade.py](file:///e:/Agent/backend/app/degrade.py)），工具实现者不碰判定逻辑。

**源码定位**：[schemas/meta.py](file:///e:/Agent/backend/app/schemas/meta.py) · [degrade.py 的 build_tool_meta](file:///e:/Agent/backend/app/degrade.py)
**demo**：第 1 章打印了一个 STALE_CACHE 状态的完整 meta JSON。

## 2. 降级语义 —— 源系统挂了，怎么「降」而不是「崩」

**是什么**：适配器层把"源系统异常"翻译成**五种明确的降级状态**，而不是把异常抛给上层：

| 状态 | 触发条件 | 用户可见表现 |
|---|---|---|
| `fresh` | TTL 内命中缓存 | 正常展示（不打源系统） |
| `live_ok` | 回源成功（同时写缓存） | 正常展示 |
| `stale_cache` | 回源失败（超时/5xx/未配置）+ 有历史缓存 | 展示旧数据 + "非实时"警示 |
| `unavailable` | 回源失败 + 无缓存 | "系统暂时无法访问，请稍后重试" |
| `write_failed` | 写操作失败（不降级不重试） | 逐条返回失败原因（如"该书已被预约"） |

**核心原则：无静默失败（R4.4）**——宁可明确说"这是 2 小时前的旧数据"，也不让用户误以为是实时数据。三条硬规则：

1. **读操作**（查课表/成绩/借阅）：超时重试 2 次（tenacity 指数退避 200ms→600ms），重试耗尽后进入降级链路。
2. **写操作**（续借）：**0 次重试**（AC4.5），失败立即返回 `write_failed` + 原因透传，防止 ILS 重复写。
3. **源 5xx 与超时同等处理**：`httpx.HTTPStatusError` 与 `TimeoutException` 都进入 `_DEGRADEABLE` 异常组（[adapters/base.py](file:///e:/Agent/backend/app/adapters/base.py)），这是审查修复的关键点——之前 5xx 会穿透降级链路直接 500。

**降级链路伪代码**（真实实现在 `BaseAdapter._fetch_with_cache`）：

```python
if ttl > 0 and cache.hit(key):        # TTL 内
    return FRESH(value)
try:
    data = await fetch()               # 读：内部已含 2 次重试
    cache.set(key, data, ttl)
    return LIVE_OK(data)
except (Timeout, HTTPStatusError, NotConfigured):
    if cache.has_stale(key):           # 忽略过期的历史值
        return STALE_CACHE(stale_value)
    return UNAVAILABLE(None)
```

**为什么用异常翻译而不是让调用方 try/except**：调用方（工具层）永远拿到结构化 `AdapterResponse`，不需要理解每种源系统的异常类型；新增一种故障模式只改适配器层。

**源码定位**：[adapters/base.py](file:///e:/Agent/backend/app/adapters/base.py)（`_fetch_with_cache` / `_request_with_retry`）· [adapters/library.py](file:///e:/Agent/backend/app/adapters/library.py)（写失败路径）
**demo**：第 2 章实测了 A~E 五种场景，C/D/E 都没有抛异常。
**测试**：[test_degrade_and_stale.py](file:///e:/Agent/backend/tests/test_degrade_and_stale.py) 用 respx mock 源系统，断言"5xx → STALE_CACHE 而非 500""写失败 call_count=1"。

## 3. is_stale 状态标注 —— 「陈旧」是可计算的判定

**是什么**：一条判定规则 + 一张 TTL 分域表（[stale.py](file:///e:/Agent/backend/app/stale.py)）：

```
is_stale = (degrade_status in {STALE_CACHE, UNAVAILABLE})
        or (source == CACHE and now - synced_at > ttl_for_domain)
```

| 数据域 | TTL | 说明 |
|---|---|---|
| 课表 | 15 分钟 | 选课/调课高峰期收紧到 5 分钟 |
| 借阅 | 5 分钟 | 涉及"是否可续借"决策 |
| **成绩** | **0（永不缓存）** | 红线 R3：成绩不缓存，任何非实时来源判陈旧 |
| 订阅/工单 | —（internal） | 写内部库，永不 stale |

**设计要点**：

1. **纯函数**：`compute_is_stale(source, synced_at, ttl, degrade_status, now)` 相同输入必得相同输出，可单测穷举（测试用 freezegun 冻结时间）。
2. **TTL 一个参数表达整条红线**：成绩域 ttl=0，意味着"不缓存"不是一句注释，而是判定规则的一部分。
3. **缓存过期时间基于 `time.monotonic`**（[cache.py](file:///e:/Agent/backend/app/cache.py)），不受系统时钟回拨影响，也不受测试时间冻结干扰——业务时间戳（synced_at）与过期判定（monotonic）分离。
4. **溯源与新鲜度独立**：`source/synced_at` 回答"数据从哪来"，`is_stale` 回答"还能不能信"，两者不混用。

**用户可见表述（R5.3）**：`is_stale=true` 时展示"以下为 15 分钟前的数据"；`unavailable` 时展示"系统暂时无法访问"。话术模板集中在 [templates/degrade.yaml](file:///e:/Agent/backend/app/templates/degrade.yaml)，按 mtime 热更新（改 yaml 即时生效，不用发版）。

**demo**：第 3 章穷举了 4 种典型组合的判定结果。

## 4. 写操作三道闸 —— 确认态 / 幂等 / 会话频控

**是什么**：`library_renew` 是全系统唯一的白名单写操作，执行前有三道闸（[tools/library.py](file:///e:/Agent/backend/app/tools/library.py)）：

```
闸1 确认态：params.confirmed 必须为 True
            （编排层必须先展示新到期日、用户确认后才能置 True）
      ↓
闸2 幂等：  idempotency_key = sha256(session_id + 排序后条码 + 日期)
            同 key 重放返回上次结果，ILS 只被调用一次
      ↓
闸3 频控：  每会话 ≤ 10 次，超出抛 PreconditionError
```

**为什么**：LLM 的工具调用是**概率性**的——模型可能"热心地"帮你重复执行、在没展示到期日时就直接续借、或陷入循环调用。三道闸保证"模型失控"最多变成一次明确的拒绝（PreconditionError → 422），而不是一次真实的重复写。

**关键设计决策**：

1. **闸在工具层，不在提示词里**。就算模型"想"绕过，契约层根本不存在 `confirmed=False` 的执行路径——提示词是软约束，validate() 是硬约束。
2. **幂等存储是进程内 dict**（`Services.idempotency`），注释明确标注"生产迁移 Redis / DB 唯一约束"。dev 阶段够用且零配置，迁移点收敛在 `Services` 一个类上。
3. **审计与幂等的顺序**：dispatch 的 `finally` 写审计（无论成败），幂等命中也会留痕——"重放"本身也是需要审计的事件。

**demo**：第 4 章用桩适配器实测：未确认 → 拒绝（ILS 调用 0 次）；同 key 重放 → ILS 调用仍是 1 次；第 11 次 → 频控拒绝。

## 5. Function Calling Schema —— 工具怎么「翻译」给 LLM

**是什么**：6 个工具（只读 4 + 写 1 + 兜底 1）各自声明 `ToolSpec`（[tools/base.py](file:///e:/Agent/backend/app/tools/base.py)）：

```python
ToolSpec(
    name="library_renew",
    description="续借图书。必须先向用户展示新到期日并获确认。",
    params_model=LibraryRenewParams,     # ← JSON Schema 从这里派生
    result_model=LibraryRenewResult,
    preconditions=("已展示新到期日并获用户确认", ...),
    postconditions=("审计留痕", ...),
    write=True,                          # 白名单写标记
    boundary="AI+H",                     # 人机协同边界
)
```

`registry.openai_tools()` 一次性导出全部工具为 OpenAI `tools` 参数。

**为什么字段描述如此重要**：LLM 看不到 Python 函数，只能看到 JSON Schema 的 `description`。`student_id` 的描述固定为"以会话身份注入，禁止作为用户输入"（STUDENT_ID_DESC 常量）——这是越权风险 K2 的第一道防线：**即使模型想帮别人查成绩，Schema 契约层也不给它传学号的合法路径**（工具执行时一律用 `ctx.student_id`，忽略外部传入值）。

**手写 vs 派生**：`parameters` 属性直接返回 `params_model.model_json_schema()`。手写 Schema 会在模型演化时漂移（文档说 required、代码里 optional），派生则物理上不可能不一致。

**Schema 类型三分类**（决定工具的实现策略）：

| 类型 | 工具 | 特征 |
|---|---|---|
| 只读 | timetable / grade / loans / (reminder 查询) | 走缓存降级链路，带 meta |
| 白名单写 | library_renew | 三道闸 + 0 重试 + 幂等 |
| 兜底 | handoff_create | 写内部工单库，永不拒答（置信度低时转人工） |

**demo**：第 5 章打印了 6 个工具清单和 library_renew 的 Schema properties。

## 6. 审计与脱敏 —— 记动作，不记数据

**是什么**：dispatch 的 `finally` 中写审计（[logging_util.py](file:///e:/Agent/backend/app/logging_util.py)）：

```
audit_log: ts / student_id(脱敏) / session_id / action / tool_name
           / args_digest(参数摘要) / result / latency_ms / channel
```

**两条硬约束**：

1. **student_id 落库前必脱敏**：`mask_student_id("20230001") → "2023****01"`。审计库泄露也无法定位到个人（R3.4）。
2. **成绩明细不入库**：审计只有"查过成绩"这个动作 + 参数摘要（barcodes 变成 `<3 items>`、idempotency_key 变成 `<hash:ab12cd34…>`），没有成绩本身。

**为什么"最小化"**：审计是排障与合规的唯一事实来源，但审计库本身也是攻击面——存得越少，泄露的爆炸半径越小。

**工程细节**：

- `write_audit` 自带 `commit()`，审计提交与业务提交独立——业务回滚不抹掉"发生过什么"。
- 审计失败不阻断主流程（dispatch 中 try/except 隔离，只记日志）。
- handoff 工单同样脱敏存储 + `retrieved_facts` 只存摘要（R1.5）。

**demo**：第 6 章查询了一次真实落库的审计行，展示脱敏后的 student_id。
